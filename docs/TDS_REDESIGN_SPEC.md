# TDS-first 4개 앱 리디자인 설계서

작성일: 2026-08-25

## 1. 목적

이 설계는 AIERS Apps in Toss 수강생 키트의 4개 서비스를 TDS 중심으로
리디자인하고, 같은 원본에서 생성되는 starter 4개와 complete 4개를 함께
개선하기 위한 기준이다.

최종 결과는 다음 세 가지 목적을 동시에 만족해야 한다.

1. 앱인토스 안에서 이질감이 적은 TDS 기반 모바일 경험을 제공한다.
2. 네 서비스가 서로 다른 문제와 핵심 사용 루프를 분명하게 보여준다.
3. 스크린샷 한 장과 약 30초 영상만으로 서비스 맥락과 결과를 이해할 수 있다.

검증 기준은 원본과 오버레이에서 재생성한 8개 프로젝트가 모두 빌드되고,
각 complete 예제의 390×844 대표 흐름이 TDS, 토스페이스, 접근성 기준을
만족하며 약 30초 안에 서비스 가치를 전달하는 것이다.

## 2. 확정한 방향

선택한 방향은 `TDS-first, product-specific`이다.

- TDS가 레이아웃, 정보 위계, 입력, 버튼, 상태 피드백의 공통 문법을 맡는다.
- 앱별 개성은 강조색, 토스페이스 이모지, 콘텐츠, 핵심 결과 경험에 남긴다.
- 토스 로고나 토스의 고유 서비스 화면을 복제하지 않는다.
- “토스스럽다”는 표현은 절제된 정보 구조, 명확한 한 화면 한 목적,
  안정적인 하단 행동, 짧고 친절한 문구, 즉시 이해되는 상태 피드백을 뜻한다.
- 과한 그라데이션, 겹친 카드, 강한 그림자, 장식용 영문 라벨은 제거하거나
  최소화한다.

### UI/UX Pro Max 선별 결과

보조 디자인 검토에서 다음 항목을 채택한다.

- 최소 44×44px 터치 영역
- 명시적 입력 라벨과 오류 안내
- 빈 상태의 다음 행동
- 한 화면 1~2개 이내의 절제된 모션
- `prefers-reduced-motion` 대응
- 모바일 폭별 텍스트 및 컨테이너 적합성 확인

별도 Vibrant 스타일, 독립 팔레트, Google Fonts, Phosphor 또는 Heroicons는
TDS와 중복되거나 충돌하므로 채택하지 않는다. 토스페이스를 일반 기능
아이콘처럼 쓰지 않고, TDS 아이콘과 역할을 나누는 방식으로 사용자 요청과
접근성 원칙을 함께 만족시킨다.

## 3. 생성 구조와 수정 경계

`starter-kits/*`와 `complete-examples/*`는 생성 결과물이다. 직접 수정하지
않는다.

수정 원본은 다음과 같다.

- 공통 앱 셸, 스타일, 라이선스, 공통 UI:
  `tooling/base`
- 앱별 화면과 모델:
  `tooling/overlays/<kit>/shared`
- starter와 complete의 설명 및 선택 확장:
  `tooling/overlays/<kit>/starter`,
  `tooling/overlays/<kit>/complete`
- 앱 이름, 색상, 태그라인:
  `tooling/kits.mjs`

변경 후 `tooling/scripts/generate-kits.mjs`로 8개 결과를 다시 생성한다.
starter와 complete는 같은 핵심 루프와 디자인 언어를 공유하되 기존 교육
계약을 보존한다.

- 주말 활동 complete: 무료 활동 자동 우선 정렬
- 습관 챌린지 complete: 3일 연속 달성 축하
- 여행 테스트 complete: 결과 문구 복사 상태
- 선물 추천 complete: 예상 가격 상세

## 4. 공통 화면 구조

기존의 별도 브랜드 헤더와 큰 공통 카드 셸을 제거하고, 기능 화면 자체가 앱의
첫 화면이 되도록 단순화한다.

기본 구조는 다음 순서를 따른다.

1. TDS `Top`으로 현재 화면의 목적과 짧은 설명을 전달한다.
2. 필요한 경우 `SegmentedControl`, `Tab`, `ProgressBar`로 현재 위치를 보인다.
3. 주요 정보는 `ListRow`, 입력은 TDS `TextField` 또는 `TextArea`로 표현한다.
4. 결과나 상태는 `Badge`, 진행 컴포넌트, 짧은 결과 영역으로 강조한다.
5. 다음 핵심 행동은 `FixedBottomCTA` 또는 의미상 적합한 `Button`으로 고정한다.
6. 저장, 완료, 복사와 같은 짧은 결과는 `Toast`로 확인시킨다.

공통 테스트 광고 패널은 개발 환경에서만 표시하되 대표 스크린샷과 촬영
화면에서는 보이지 않아야 한다.

## 5. 앱별 서비스 구조

### 5.1 이번 주말 뭐하지?

핵심 가치: 가까운 곳에서 할 일을 빠르게 발견하고 내 주말 목록에 저장한다.

대표 흐름:

1. 전체 또는 카테고리별 활동을 둘러본다.
2. `ListRow`에서 장소와 예상 시간을 비교한다.
3. 상세 화면에서 설명, 장소, 시간, 무료 여부를 확인한다.
4. `FixedBottomCTA`로 활동을 저장한다.
5. 저장 완료 `Toast` 후 저장 목록에서 방금 선택한 항목을 확인한다.

주요 TDS 구성:

- `Top`
- `SegmentedControl`
- 카테고리 필터
- `ListRow`
- `Badge`
- `FixedBottomCTA`
- `Toast`

토스페이스는 활동 종류와 상세 대표 비주얼에 사용한다. 저장, 뒤로가기,
화살표 같은 기능 의미는 TDS 아이콘을 사용한다.

### 5.2 작은 습관 챌린지

핵심 가치: 오늘의 작은 습관을 기록하고 연속성을 눈으로 확인한다.

대표 흐름:

1. 오늘의 습관과 현재 연속 기록을 확인한다.
2. 실천 완료를 선택한다.
3. 한 줄 기록과 선택적 기분을 남긴다.
4. 완료 피드백과 갱신된 연속 기록을 확인한다.
5. 최근 기록 또는 주간 진행 화면으로 재방문한다.

주요 TDS 구성:

- `Top`
- `SegmentedControl`
- `Badge`
- `TextArea`
- `ListRow`
- `ProgressBar` 또는 의미상 적합한 진행 컴포넌트
- `FixedBottomCTA`
- `Toast`

토스페이스는 습관, 기분, 연속 달성 표현에 사용한다. complete의 3일 연속
축하는 한 화면 안에서 가장 중요한 요소 하나만 짧게 움직이게 한다.

### 5.3 여행 스타일 테스트

핵심 가치: 여섯 번의 빠른 선택으로 내 여행 성향과 실용적인 팁을 얻는다.

대표 흐름:

1. 질문 수, 예상 시간, 결과 유형을 확인하고 테스트를 시작한다.
2. 현재 질문 번호와 진행률을 확인한다.
3. 라디오 선택 형태의 행에서 답을 고르고 다음으로 이동한다.
4. 여행 유형, 설명, 키워드, 한 가지 팁을 확인한다.
5. complete에서는 결과 복사 성공 또는 차단 상태를 `Toast`로 확인한다.

주요 TDS 구성:

- `Top`
- `ProgressBar`
- 선택 가능한 `ListRow` 또는 TDS 선택 패턴
- `Badge`
- `FixedBottomCTA`
- `Toast`

토스페이스는 시작 화면과 결과 유형의 대표 비주얼에 사용한다. 결과 화면은
공유 가능한 스크린샷 구도를 고려해 결과명, 설명, 키워드, 팁 순으로 구성한다.

### 5.4 선물 추천 도우미

핵심 가치: 받는 사람, 예산, 상황을 고르고 추천 이유가 있는 선물을 얻는다.

대표 흐름:

1. 받는 사람을 선택한다.
2. 예산과 전하고 싶은 상황을 순서대로 선택한다.
3. 선택한 세 조건을 최종 확인하고 필요하면 수정한다.
4. 로딩 상태 후 추천 결과와 이유를 확인한다.
5. 오류 시 재시도 또는 로컬 추천 사용을 선택한다.
6. 결과에서 조건을 바꿔 다시 추천할 수 있다.

주요 TDS 구성:

- `Top`
- `ProgressBar` 또는 `ProgressStepper`
- 선택 행 또는 선택 버튼
- 조건 확인용 `ListRow`
- 로더
- `Badge`
- `FixedBottomCTA`
- `Toast` 또는 오류 영역

토스페이스는 받는 사람, 예산, 상황, 추천 품목 비주얼에 사용한다. 추천 결과는
순위보다 이름, 추천 이유, 가격 정보가 먼저 읽히도록 구성한다.

## 6. 토스페이스 사용 정책

사용 대상은 토스팀이 공개한 2D 토스페이스 원본이다. 3D 토스 이모지 이미지는
사용하지 않는다.

- 공식 SVG 원본 중 사용하는 14개를 `v1.6.1`로 고정해
  `tooling/base/public/tossface` 아래에 로컬 번들한다.
- 외부 CDN에 런타임을 의존하지 않는다.
- 원본을 변형, 합성, 재가공하지 않는다.
- 폰트 원본과 함께 저작권 안내 및 라이선스 전문을 포함한다.
- 앱 또는 쉽게 찾을 수 있는 문서에 다음 출처를 표시한다.
  `이 서비스에는 토스팀에서 제공한 토스페이스가 적용되어 있습니다.`
- 토스페이스는 장식과 콘텐츠 의미에 사용한다.
- 기능 버튼, 내비게이션, 상태 제어에는 TDS 아이콘을 사용한다.
- 토스페이스 글리프에는 읽기 목적이 있으면 대체 텍스트를 제공하고, 장식이면
  접근성 트리에서 숨긴다.

## 7. 색상, 간격, 타이포그래피

- 색상은 `@toss/tds-colors` 토큰을 우선한다.
- 각 앱은 한 개의 강조색만 사용하고, 본문과 배경은 TDS 회색 체계를 따른다.
- 강조색은 의미 없는 큰 배경 면보다 CTA, 선택, 진행, 작은 상태 요소에 쓴다.
- 타이포그래피는 TDS 컴포넌트의 기본 위계를 우선하고 별도 Google Fonts를
  추가하지 않는다.
- 본문 줄 길이는 모바일에서 빠르게 읽히도록 짧게 유지한다.
- 터치 대상은 최소 44×44px, 주요 CTA는 최소 48px 높이를 사용한다.
- 인접 터치 대상 사이에는 오동작을 줄일 수 있는 충분한 간격을 둔다.
- 390×844 화면에서 핵심 CTA와 현재 단계가 동시에 이해되어야 한다.

## 8. 상태와 피드백

모든 서비스는 다음 상태를 명시적으로 설계한다.

- 초기 상태
- 선택 중 상태
- 완료 또는 결과 상태
- 빈 상태
- 로딩 상태가 있는 경우 로딩 상태
- 실패 가능성이 있는 경우 오류 및 재시도 상태

빈 상태는 빈 화면으로 두지 않고 이유와 다음 행동을 함께 제공한다. 오류는
색상만으로 표현하지 않고 텍스트와 `role="alert"` 또는 적절한 live region으로
알린다. 저장, 완료, 복사 같은 짧은 피드백은 CTA 및 Safe Area와 겹치지 않는
TDS Toast를 사용한다.

## 9. 모션

- 화면 전환은 180~240ms 범위의 ease-out 진입을 기본으로 한다.
- 이탈 모션이 필요하면 더 짧은 ease-in을 사용한다.
- 한 화면에서 동시에 강조하는 움직임은 1~2개로 제한한다.
- 버튼 누름, 선택, 진행 변화가 원인과 결과를 이어주는 경우에만 움직인다.
- 장식용 반복 바운스, 스크롤 재킹, 과한 패럴랙스는 사용하지 않는다.
- `prefers-reduced-motion: reduce`에서는 전환을 사실상 즉시 표시한다.
- 영상 자동화는 UI 전환이 끝난 뒤 다음 포인터 동작을 시작한다.

## 10. 접근성

- 모든 입력은 화면에 보이는 라벨과 연결한다.
- 선택 상태는 색상뿐 아니라 체크, 텍스트 또는 접근성 상태로 전달한다.
- 아이콘 전용 버튼에는 정확한 한국어 접근성 이름을 제공한다.
- 키보드 포커스 표시를 제거하지 않는다.
- 본문은 WCAG AA 수준의 명도 대비를 목표로 한다.
- 결과, 오류, 저장 완료 등 중요한 비동기 상태는 live region으로 알린다.
- 작은 설명 텍스트가 390px 폭에서 잘리거나 겹치지 않아야 한다.

## 11. 스크린샷과 영상 설계

### 대표 스크린샷

각 complete 앱은 서비스 가치를 가장 잘 보여주는 한 화면을 기본 대표
스크린샷으로 사용한다.

- 주말 활동: 저장할 활동을 비교할 수 있는 첫 목록 화면
- 습관 챌린지: 연속 기록과 오늘 습관이 함께 보이는 화면
- 여행 테스트: 여행 유형 결과 화면
- 선물 추천: 추천 이유와 가격이 보이는 결과 화면

캡처는 390×844 기준으로 맞추고 개발 도구, 마우스 포인터, 테스트 광고 패널,
임시 토스트가 의도 없이 포함되지 않게 한다.

### 약 30초 결과 영상

영상은 다음 리듬을 따른다.

1. 첫 화면과 가치 제안 확인: 2~3초
2. 핵심 선택 또는 입력: 12~18초
3. 완료 피드백: 2~3초
4. 결과 또는 재방문 화면: 5~8초

포인터는 실제 누르는 요소의 중심에 위치하고 클릭 전후에 짧게 머문다. 화면
전환 중에는 이동하지 않는다. 선택을 불필요하게 빠르게 반복하지 않고, 각 앱의
맥락이 읽힐 만큼 문구가 보이는 시간을 확보한다.

## 12. 범위 밖

이번 리디자인에서 다음은 추가하지 않는다.

- 로그인 또는 계정 시스템
- 결제, 정산, 실서비스 수익화 연동
- 새로운 운영용 백엔드
- 원격 데이터베이스
- 토스 브랜드 로고 또는 토스 고유 화면 복제
- 토스페이스 3D 이미지
- 대표 결과물을 위한 가짜 운영 수치

기존 로컬 저장과 선택적 Mock API 범위는 유지한다.

## 13. 검증 게이트

구현 후 다음 순서로 검증한다.

1. 모델 단위 테스트와 새 상태 전이 테스트
2. `tooling/scripts/generate-kits.mjs`로 8개 결과 생성
3. 생성 결과 최신성 검사
4. 8개 프로젝트의 설정 검증, 타입 검사, 테스트, 빌드
5. 390×844에서 4개 complete 앱의 초기, 핵심 행동, 결과 화면 확인
6. 터치 대상, 포커스, 라벨, 오류 안내, reduced-motion 확인
7. 대표 스크린샷 재생성 및 시각 검토
8. 앱별 약 30초 결과 영상 재생성 및 프레임 단위 검토

starter와 complete의 선택 확장 차이가 유지되지 않거나 생성 결과를 직접
수정해야만 통과하는 경우에는 완료로 판단하지 않는다.
